# Language support

Everything the program says to a person comes from a catalog in
`locales/`, through [rust-i18n]. The user-facing rules — which variable wins,
how `Accept-Language` is honoured, what deliberately stays English — are in the
[README](../README.md#languages). This file is for whoever *writes* a message.

## The catalogs

| File | Language | Notes |
| --- | --- | --- |
| `locales/en.yml` | English | the fallback: every key must exist here first |
| `locales/zh-CN.yml` | Simplified Chinese | `zh-TW` and `zh-Hant` fall back to it |

A language is registered in two places: the file itself, and `CATALOG` in
`src/l10n.rs` (code + native name, for the language pickers and for the error
that lists the known codes). Rust-i18n embeds the YAML at build time, so a
catalog edit needs `touch src/lib.rs` before a local `cargo test`; without it
the old strings are still in the binary. (CI always builds from scratch, so
this only bites locally.)

## Key namespaces

The first segment says who owns the string. Keep to it: the i18n test's
`no_key_is_unused` check only recognises these prefixes, and a key outside them
is invisible to it.

| Prefix | Used by |
| --- | --- |
| `daemon.` | the daemon: log lines, `job-state-message`, the flip dialog, its own `--help` |
| `setup.` | the terminal front end's own scaffolding (usage, bad arguments) |
| `tui.` | the terminal menu (prompts, action lines) |
| `gui.` | the window, and `gui.window.*` is everything that appears in it |
| `config.` | validation errors, shared by both front ends |
| `common.` | strings both front ends need (e.g. the missing-ipp-usb hint) |

A front end may reuse another's keys when the sentence is genuinely the same —
the terminal menu shows `gui.window.state_idle` and `gui.window.field_note`
because those are the same words in both places, and duplicating them would
only create a chance to drift.

## Placeholders

`%{name}` substitution, checked by `tests/i18n.rs`: every placeholder in the
English value must appear in every other catalog's value for the same key, and
no catalog may introduce one of its own. Rust-i18n leaves an unknown
placeholder in the output as literal text, which is why the test exists.

## What the tests enforce

`tests/i18n.rs` fails the build for:

- a key in one catalog but not the other;
- a placeholder mismatch;
- a key used in the source but absent from the catalogs
  (`every_key_used_in_the_source_exists`);
- a catalog key nothing uses (`no_key_is_unused`) — this is what keeps the
  catalogs honest when a feature is removed;
- a language that does not speak its own language: the usage text, the terminal
  menu, the status page, `/flip` and `Content-Language` are all exercised in
  both catalogs.

`every_declared_language_follows_rfc_8011` covers the other direction: the tag
announced to IPP clients must be a lowercase RFC 8011 tag even though the
catalog is called `zh-CN`.

## Adding a string

1. Add the English value to `locales/en.yml` under the right prefix.
2. Add the same key to every other catalog, with the same placeholders.
3. Use it from the source (`t!("…")` or `l10n::tr(locale, "…", …)`); a key
   that is not used fails `no_key_is_unused`.
4. If it is a window label, add a field to `WindowLabels` in `src/gui.rs` and
   read it from the widget, the same way every other label is.
5. `touch src/lib.rs && cargo test` (or let CI do it).

## Documenting in two languages

The program is bilingual; the documentation is bilingual only where users read
it.

- `README.md` (English) and `README.zh-CN.md` (Chinese) are kept in step: a
  change to one that a user would notice is a change to both. Each starts with
  a link to the other.
- Everything under `docs/` is written in English for maintainers. `ISSUES.md`
  is kept in Chinese and predates this rule; it is a historical log, not a
  guide.
- Code comments and commit messages are English, because they end up in `git
  log` next to the English identifiers.
